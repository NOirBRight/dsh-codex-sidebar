The Browser tool uses one Host-managed persistent Chromium profile for every http(s) page. The client renders the active Page through a bounded versioned frame stream and sends pointer, wheel, keyboard, and IME input back to that Page. iframe, pick-proxy, and a split embedded/managed policy were rejected. A page that merely permits framing still cannot guarantee DOM access, exact screenshots, or the same automation contract. One managed implementation gives local and external pages the same behavior.

Entering 批注 captures an exact viewport screenshot and visible DOM/a11y boxes from the same managed Page. Scrolling temporarily resumes the page; stopping captures a new immutable view. A Browser 批注 cannot be added without this evidence. One viewport image plus the target rect is sent with each Browser 批注; Files and Review remain text-only.

The accepted spike at `.scratch/managed-browser-live-prototype/` established the initial performance requirements: bounded latest-frame work, no per-input HTTP requests, draggable scrollbars, and scrolling while 批注 stays active. Managed Browser v2 replaces its geometry assumption with one Host-owned `BrowserLayout`. The committed CSS viewport, client container, and encoded media dimensions are separate. `Page.screencastFrame` is only a dirty signal; its device dimensions cannot select the screenshot clip, Canvas surface, input mapping, or 批注 coordinates.

Each WebSocket must send a protocol-v2 client hello within five seconds. The Host fails closed otherwise, then publishes the layout policy and initial layout commit. Input names the presented layout revision. JPEG acknowledgements name sequence, revision, and media generation. A layout change releases the old outstanding fallback frame, drops captures completed for the old generation, and keeps the previous client presentation until the first matching new-generation frame is ready.

Direct Browser media uses a separate, video-only WebRTC peer owned by the authenticated control connection. Signaling stays on that connection, accepts bounded SDP and candidate data, rejects TURN configuration, and matches the exact connection owner, layout revision, and media generation. The encoder Page is created from the managed Chromium context through a narrow lease, receives pixels and JSON commands only, and never injects the target Page. Timeout, capacity, encoder, or peer failure immediately retains the JPEG route; retry is cooldown-limited.

JPEG fallback keeps the screencast as a change source and acknowledges each CDP source frame immediately. A bounded `Page.captureScreenshot` uses only the committed CSS viewport and may lower JPEG quality or encoded scale without changing layout. Desktop Origin connections use binary v2 frames; Origin-less Mobile connections use JSON Base64 v2 with a 96 KiB encoded-JPEG ceiling. Each stream permits at most one screenshot capture, one delivered but unacknowledged frame, and one latest dirty request. The client acknowledges after paint and also after a matching frame cannot be decoded. Stale, future, and duplicate acknowledgements do not advance the stream.

The persistent Chromium profile keeps cookies and site storage. Before launch, the Host performs a read-only, no-follow size estimate over allowlisted derived-cache directories such as `Cache`, `Code Cache`, and `GPUCache`; it never renames, removes, or repairs profile paths. Chromium's persistent-context startup owns singleton arbitration, including concurrent launch attempts and stale ownership data. After one context starts successfully, an estimate above `managedBrowser.cacheBudgetBytes` creates one temporary blank Page and CDP session, enables the Network domain, and calls `Network.clearBrowserCache`. The session and Page are detached and closed after success or failure. Failure emits a warning without discarding the context. This Chromium-owned operation clears browser cache without clearing cookies, Local Storage, or IndexedDB. Chromium also receives matching disk and media cache limits for future growth.

The existing `browser_tabs`, `browser_open`, `browser_snapshot`, `browser_click`, and `browser_fill` tool names remain. Their implementation moves from the client iframe DriveHub to the managed Page; refs become document-scoped and stale after navigation.
