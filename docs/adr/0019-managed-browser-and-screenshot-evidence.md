The Browser tool uses one Host-managed persistent Chromium profile for every http(s) page. The client renders the active Page through a bounded binary screencast and sends pointer, wheel, keyboard, and IME input back to that Page. iframe, pick-proxy, and a split embedded/managed policy were rejected. A page that merely permits framing still cannot guarantee DOM access, exact screenshots, or the same automation contract. One managed implementation gives local and external pages the same behavior.

Entering 批注 captures an exact viewport screenshot and visible DOM/a11y boxes from the same managed Page. Scrolling temporarily resumes the page; stopping captures a new immutable view. A Browser 批注 cannot be added without this evidence. One viewport image plus the target rect is sent with each Browser 批注; Files and Review remain text-only.

The accepted spike at `.scratch/managed-browser-live-prototype/` established the initial performance contract: binary WebSocket frames, 30 FPS cap, latest-frame backpressure, no per-frame Canvas resize, no per-input HTTP requests, draggable scrollbars, and scrolling while 批注 stays active. Its automated run measured a 16.8 ms p95 frame gap, zero Canvas resize mutations, and successful normal/批注 scroll interaction on the lab machine.
The production stream keeps the screencast as a change source and acknowledges each CDP source frame immediately. Visible frames use a bounded `Page.captureScreenshot` clip of the current visual viewport. Desktop Origin connections retain binary v1 frames at up to 10 FPS, JPEG quality 80, and 1.5× scale; Origin-less Mobile connections use JSON Base64 at up to 4 FPS, quality 65, and 1× scale. The versioned frame fields continue to report CSS viewport dimensions so input and 批注 coordinates remain CSS-pixel based.

Each WebSocket must send a versioned client hello within five seconds. The Host fails closed otherwise, then answers a ready message that selects the frame encoding and `frame-ack-v1` flow control. The Host permits at most one screenshot capture, one delivered but unacknowledged frame, and one latest dirty request per stream. The client acknowledges after Canvas paint and also after a frame cannot be decoded, so a corrupt JPEG cannot stall the stream. Stale, future, and duplicate acknowledgements do not advance the stream. A timer delivers the last dirty request when it arrived inside the frame interval; a later source event is not required.

The persistent Chromium profile keeps cookies and site storage. Before a new Chromium singleton starts, the Host totals only allowlisted derived caches such as `Cache`, `Code Cache`, and `GPUCache`. If no live singleton owns the profile and the total exceeds `managedBrowser.cacheBudgetBytes`, it removes those real directories without following symlinks. Cleanup failure emits a warning and does not prevent launch. Chromium also receives matching disk and media cache limits.

The existing `browser_tabs`, `browser_open`, `browser_snapshot`, `browser_click`, and `browser_fill` tool names remain. Their implementation moves from the client iframe DriveHub to the managed Page; refs become document-scoped and stale after navigation.
