# Managed Browser has one layout authority and separate control and media planes

The Host owns one revisioned `BrowserLayout` for each Browser Tab. It commits the selected mode, CSS viewport, and media generation only after the exact target Page reports matching viewport metrics. While a proposal or verification applies, the target remains owned by its control connection but is unavailable to visual reads, media capture, and input. Every entered layout operation advances an internal epoch; results begun under an earlier epoch are discarded even when revision and media generation did not change. The client buffers a desktop press/release pair into one `tap` or `drag`, and the Host dispatches that complete gesture while it owns one input lease; the wire protocol rejects partial pressed-pointer messages, so a gesture cannot span a viewport write. The Host reads CSS layout dimensions from CDP rather than page-world properties and applies the device scale factor selected when it launched Chromium. If Playwright completes a viewport change without satisfying that postcondition, the Host applies a CDP device-metrics override and verifies again. Post-screencast verification reapplies those device metrics even when the reported CSS dimensions already match, because Chromium can retain an older compositor surface without changing them. Before untrusted navigation, the Host installs a random, immutable main-world paint function that closes over Chromium's native `Promise` and `requestAnimationFrame`. After the CSS postcondition succeeds, the Host brings the exact target forward, forces one low-quality CDP capture, awaits two native animation frames through that function, and forces a second capture before the layout can commit; page script cannot replace the captured functions, redirect the real global object lookup, or report an early success, and timeout invalidates the target. Layout proposals serialize one `stopped`/`gated`/`active` screencast lifecycle: an existing screencast stops before the viewport write, restarts in `gated`, and becomes `active` only after post-start CSS and compositor verification. The Host publishes `layout-commit` only after that post-start verification, because `Page.startScreencast` can temporarily restore an older compositor surface. Frames received in `gated` are acknowledged and coalesced into the explicit final-generation capture; every source frame received in `active` remains a real dirty signal, so the Host never guesses whether an event is a screenshot echo. Screencast start, stop, and cleanup commands share a bounded deadline; the first terminal failure closes the owner synchronously for queued lifecycle work, while replacement cleanup and the next owner continue after that deadline. A second failure invalidates the target instead of publishing a layout that Chromium did not apply. The same verification guards an otherwise unchanged layout. A fixed-layout connection also verifies the exact committed layout after its first screencast starts, before accepting that screencast as a capture trigger or starting direct-media negotiation; this repairs viewport drift without advancing the revision or media generation and fails closed if another layout or target became current. The client keeps its local container size, the committed CSS viewport, and encoded media dimensions as separate values. The JPEG route defines encoded scale in CSS pixels and divides the CDP clip scale by the applied device scale factor, so forced high-DPI metrics do not multiply Desktop 1.5× or Mobile 1× output a second time. Selecting a fixed preset produces exactly one `layout-propose` on the owning control WebSocket; persisted UI state, stream-ticket issuance, and the Browser adapter do not commit layouts out of band. Fixed presets do not consume container measurements; fit measurements settle before one proposal. Mobile opens its hidden IME only after a completed touch tap; touch scrolling does not open it, and fit proposals remain paused until the IME blurs. Desktop focus does not pause fit. A media frame, Canvas backing size, WebRTC video size, or `Page.screencastFrame` device metadata cannot resize Chromium or replace the committed viewport.

The authenticated Browser WebSocket is the always-available control plane. It carries protocol negotiation, layout proposals and commits, revisioned input, page state, WebRTC signaling, route state, and bounded JPEG fallback. Each connection binds one opaque managed Page/CDP record identity. Removing that record synchronously invalidates only the connection with the same identity before CDP or Page teardown starts; every awaited visual read, input, paint, tracked rectangle, and media capture freezes and rechecks the exact Page, document, layout, and internal transition epoch before it can publish a result or continue a compound gesture. A matching revision is required for input, and a matching revision plus media generation is required for fallback acknowledgements. The client retains the last good presentation across a layout change and switches presentation and coordinate mapping together after media for the new generation is ready.

Browser surface actions keep the originating Tab identity across asynchronous screenshot and evidence work. Both ends of an evidence selection must use the same presented layout revision; a layout change during the gesture cancels the selection instead of combining coordinates from different viewports. A completed capture or evidence commit is applied only to that exact Browser Tab even if another Tab became active while the request was pending.

Direct media uses a Browser-owned, video-only WebRTC peer when STUN-only ICE succeeds. The receive peer is constructed with empty `iceServers` (host candidates only, never TURN). The encoder Chromium disables `WebRtcHideLocalIpsWithMdns` so those host addresses are usable between the GUI and the isolated encoder Page on the same machine. It is independent from Mobile Pairing and never requests camera, microphone, or audio. The Host encoder is isolated from the target Page and receives pixels only. Its configurable JPEG capture profile always uses the Host-committed viewport and is independent from the control socket's fallback profile, so an Origin-less Mobile connection keeps the 96 KiB tunnel ceiling without imposing that ceiling on encoder input. Negotiation failure selects JPEG fallback without interrupting control. Retry is bounded by cooldown and an explicit lifecycle signal; TURN and continuous retry are rejected. Each direction accepts at most 64 ICE candidates per attempt, including the end marker; pre-description client candidates cannot grow beyond that limit. A Browser surface remains mounted but hidden and inert when another tool Tab is active. The client reports that visibility change with the exact owner, layout revision, and media generation while the hidden grace keeps its control connection alive. Visibility recovery cancels teardown; grace expiry closes the control connection and releases the peer and encoder while preserving the target Page. Authoritative `session/disposed` releases that session's control sockets, managed Pages, and cached file port. Plugin shutdown gives sockets, target cleanup, and started work one configured deadline, then stops waiting for unresponsive cleanup.

The client exposes direct video, low-bandwidth fallback, reconnecting, and unavailable as distinct presentation states. It does not claim direct video until the exact current generation has decoded its first frame. Video slots default to `opacity:0` and stay in the compositor so Chromium can decode a pending first frame; the committed slot is marked `data-dcs-presenter`. React does not own `hidden` or canvas `opacity`. Pointer and wheel land on one hit layer above inert video/Canvas (`z-index:3`, `touch-action:none`) and below 批注 badges (`z-index:4`). Desktop interaction latency is the direct-video route; JPEG fallback stays an interaction-first, ack-limited ceiling for constrained tunnels and is not the desktop latency target. `display:none` on a pending video is rejected because it prevents presentation and forces JPEG fallback. The active video and fallback Canvas use the same centered `contain` geometry. Any local condition that prevents presentation declines that owner, layout revision, and media generation; a stale receiver cannot decline a replacement generation.

JPEG fallback is an interaction-first route for constrained Mobile tunnels. Every connection retains at most one capture, one unacknowledged frame, and one latest dirty request. Its configured frame interval is a hard capture-rate ceiling. A passive source waits one task before capture so an immediately following input can replace it; only that first input forms the barrier, so a continuous wheel stream still publishes intermediate frames instead of waiting for the entire input backlog to drain. Interaction, navigation, refresh, and layout commits replenish a bounded passive-frame budget, so the latest resulting repaint is delivered but animation alone eventually stops producing fallback frames. Encoding may lower JPEG quality or encoded resolution to meet the configured byte ceiling, but it cannot change the committed CSS viewport. Exact Browser evidence remains a separate capture from the target Page. Its RPC transport requires an explicit byte offset and returns at most 96 KiB of raw JPEG as Base64 per response, including total size and the next offset, so one response stays below the Mobile tunnel's 200 KiB plaintext ceiling. Host-side model attachment reads remain local and do not traverse that RPC.

The stream exposes fixed-memory diagnostics without page URLs or content. They include layout revision/generation gauges; capture, fallback encode/send, encoder Canvas paint, and fallback acknowledgement latency aggregates; encoded bytes and route-budget drops; media outcomes; and current peer, encoder Page, capture, socket, and timer gauges. These diagnostics do not alter the existing `resources()` fields used to prove socket, timer, capture, unacknowledged-frame, and peer teardown. At media capacity, the oldest hidden owner is released by exact identity before any negotiating fallback owner. A visible connected owner is not a capacity victim, admission falls back when none is safe to release, and `maxMediaPeers` cannot exceed the encoder Page budget.

The Browser surface publishes one non-sensitive `data-browser-presentation` JSON value for local diagnostics. It records connection state, committed and presented layout identities, viewport, encoded and surface sizes, media route, the single active Canvas or video slot, and active video intrinsic size, but never URL, title, page content, or signaling data. Canvas records the identity of the frame it accepted, and a staged video retains the identity that created that slot; diagnostics never infer presenter identity from layout state. Each write replaces one complete state after its DOM presenter switch. A negotiated direct route remains reconnecting until the exact video identity presents its first frame and commits its DOM slot, then the presenter, diagnostic attribute, and user-visible route switch together. Disconnect replaces layout and presenter fields with explicit null or none values. The attribute is observational: neither layout proposals nor presentation geometry read it.

The older model, where screencast device dimensions selected screenshot and client viewport dimensions, was rejected because CDP reports device screen dimensions rather than the controlled Page layout viewport. WebRTC without the revisioned layout model was also rejected because replacing the carrier would preserve the geometry feedback loop.
